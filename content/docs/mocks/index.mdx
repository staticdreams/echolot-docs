title: Mocks
description: Serve an OpenAPI spec as a local mock server, choose what it answers, check requests against the spec, and share it on the network.
---

A mock answers every operation of a spec with the responses the spec documents, on a port of your Mac. Front ends,
apps and tests can use it before the API exists, or while the real one is down. Requests that break the spec get a
`400` that says why, so the mock also tells you when a client sends the wrong thing.

The spec is the only source of what a mock answers: its examples, or a body made from its schemas. To change an
answer, change the [spec](/docs/specs), or add [routes in JavaScript](/docs/mocks/scripted-routes).

Open the page with **Mocks** in the sidebar's module switcher, or <kbd>⌘</kbd><kbd>4</kbd>.

## Creating a mock

You need a spec in the workspace first; the Alpenglow example has `alpenglow.yaml`. Then:

1. Click **+** in the sidebar's **Mocks** header (or **New Mock** on the empty page).
2. Choose **Mock of Alpenglow demo shop**, or the spec you want.

The new mock takes the next free port from `4010`. Its settings are a file in the workspace's `mocks` folder, so a
team shares its mocks through Git.

## Starting and stopping

Click **Start** (<kbd>⌘</kbd><kbd>R</kbd>). The bar at the top shows the mock's address, such as
`http://127.0.0.1:4010/v1`: when the spec's server URL has a path (`https://demo.echolot.dev/v1`), the mock answers
under it. Requests may leave that path out, too. The copy button next to the address copies it.

Try it from Terminal:

```sh
curl http://127.0.0.1:4010/v1/products/TNT-MH-2P
```

**Stop** stops it. The sidebar shows which mocks run: a green dot, and the port beside the spec's title
(`Alpenglow demo shop · :4010`), or `stopped`. Right-click a mock for **Start** or **Stop** and **Delete…**. Delete asks
first; the settings file goes to the Trash and the spec stays.

Mocks run while their workspace window is open. A running mock picks up changes to its spec and settings without
stopping. A port another program uses can't be taken: Echolot says so; choose another port.

### Sending requests to the mock

**Use in Environment** (while the mock runs) makes an environment named `Mock: <name>` whose `{{baseUrl}}` is the
mock's address, and makes it active. Requests that start with `{{baseUrl}}`, such as the ones
[Generate Requests](/docs/specs#requests-that-follow-the-spec) makes from a spec, then go to the mock until you choose
another environment. See [Environments](/docs/workspaces/environments).

## Settings

| Setting | What it does |
| --- | --- |
| **Name** | The mock's name in the sidebar. |
| **Spec** | The spec it serves. **Open** opens it on the Specs page. |
| **Port** | The port it listens on, from 1 to 65535. |
| **Answer other devices on the network** | Listens on every network interface, for testing from a phone or a container. Off: only this Mac reaches it. |
| **Delay** | Milliseconds to wait before each answer, up to 60,000, to try a slow API. |
| **Failures** | The percentage of requests that get an injected `500`, to try how a client copes. |
| **Checks** | **Refuse requests that break the spec (400 with the reasons)**. On by default. |

## Which response a request gets

For each request, the mock finds the operation by method and path. Literal path segments win over parameters, so
`/pets/mine` is chosen before `/pets/{id}`. Then it picks the response, in this order:

1. What the request asks for: a `Prefer: code=404, example=empty` header, or Postman's `x-mock-response-code` and
   `x-mock-response-name` headers.
2. The response chosen for the operation in the **Responses** card.
3. The operation's first success response.

The **Responses** card lists every operation with a menu: **First success**, or one of the documented statuses, and
for a status with several examples, the example. The choice is saved with the mock.

The body is the response's named example (the one asked for, or the first), its single `example`, or else a body
made from its schema. When the spec documents several media types, the request's `Accept` header picks one. The
documented headers and content type are sent too. A `204`, a `304` and answers to `HEAD` have no body.

Other answers the mock gives:

| Status | When |
| --- | --- |
| `400` | Checks are on and the request breaks the spec: a missing or mistyped path, query, header or cookie parameter, the wrong content type, or a body that doesn't match its JSON Schema. The body lists every reason. |
| `404` | The spec has no operation for the path. |
| `405` | The path exists, but not with this method. The `Allow` header lists the methods it takes. |
| `413` | The request body is larger than 32 MB. |
| `500` | An injected failure (see **Failures**). |
| `501` | The operation documents no response for the status asked for. |

Browsers may call the mock from a page on another port: it answers preflight requests and sends the CORS headers.

## The log

The bottom of the page lists the requests the selected mock answered, newest first: the time, the status, the method
and path, the example used (`generated` when the body came from the schema), and how long it took. Where a request
broke the spec, the reasons are on the lines below it. Rest the pointer on a request to see the response body, the
request's body and content type; **Copy Response** copies the body. **Clear** empties the log.

Where Apple's on-device model is available, the button beside **Clear** summarizes the log.

## Saving examples into the spec

A real response you got is often the best example. Since mocks answer only from the spec, save it there: in
[History](/docs/workspaces/history), right-click an exchange of a request that follows the spec and choose **Save as
Mock Example…**. Give it a name, such as `two tents`, and click **Save**.

The response becomes a named example of its operation's response in the spec the request follows. Choose it in the
**Responses** card, or ask for it with `Prefer: example=two tents`.

## Sharing on the network

Turn on **Answer other devices on the network** to reach the mock from a phone, a tablet or a container. Other devices
use your Mac's address on the local network, with the mock's port.

The first time, macOS may ask whether Echolot may find and connect to devices on your local network. Allow it, or other
devices can't reach the mock. You can change the answer later in **System Settings › Privacy & Security › Local
Network**.

Anyone on the network can then call the mock. Turn sharing off when you don't need it.

## From the command line

`echolot mock alpenglow.yaml` serves a spec file, and `echolot mock -w <workspace> <mock>` serves a mock of a workspace
with its settings and routes, for CI or a container. See [echolot mock](/docs/cli/mock).

Agents can start mocks and read their logs through Echolot's MCP server, and create and change mocks when the
**Mocks** toolset is on. See [Agents](/docs/ai/agents).
