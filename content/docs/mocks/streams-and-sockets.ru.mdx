Живым экранам нужны живые данные: доставка, которая движется, гонка, которая обновляется круг за кругом, датчик,
который сообщает показания каждую секунду. Мок может отправлять всё это без вашего собственного сервера:

- **Server-sent events**: ответ HTTP вместо тела отправляет события по временной шкале.
- **Маршруты WebSocket**: маршрут принимает подключения WebSocket, отправляет сообщения, как только подключение
  открылось, и отвечает на то, что присылает клиент.
- **Маршруты Socket.IO**: маршрут — это пространство имён Socket.IO, с событиями, ответами и подтверждениями.
- **MQTT-брокер** рядом с моком: клиенты подписываются и публикуют, как с любым брокером, и получают сообщения,
  которые публикует мок.

Всё это создаётся вручную в редакторе мока, как и другие [маршруты](/docs/mocks/routes), и сохраняется в файле мока.
Для логики и состояния пишите сокеты на [JavaScript](/docs/mocks/scripted-routes#sockets).

## Временные шкалы [#timelines]

Потоки и сокеты отправляют свои сообщения по временной шкале. У каждого сообщения есть:

| Поле | Что это |
| --- | --- |
| **ms** | Миллисекунды после предыдущего сообщения (или после начала — для первого), до часа. |
| Событие | Для server-sent events — поле `event:`; для Socket.IO — отправляемое событие (`message`, если пусто). |
| ID | Для server-sent events — поле `id:`. |
| Данные | Что отправляется. Здесь могут быть тестовые данные и части запроса, как в [теле маршрута](/docs/mocks/routes#bodies-with-fake-data). |

Данные также читают `{{stream.index}}` (номер сообщения на шкале, с 0), `{{stream.number}}` (с 1) и
`{{stream.round}}` (какой проход шкалы, с 0), так что шкала, которая проигрывается снова, может считать круги:

```json
{ "lap": {{stream.number}}, "at": "{{$isoTimestamp}}" }
```

Время тоже можно сдвигать: `{{$isoTimestamp('-90s')}}` — это 90 секунд назад, `{{$timestamp('1h')}}` — через час. См.
[динамические значения](/docs/requests/dynamic-values).

**Проиграть** задаёт, сколько раз проигрывается шкала; `0` проигрывает её, пока клиент не уйдёт. Меню рядом выбирает,
что происходит после последнего сообщения: **завершить ответ**, **закрыть соединение** или **держать открытым**.

## Server-sent events [#server-sent-events]

Откройте ответ маршрута HTTP и нажмите **Транслировать Server-Sent Events вместо этого** под его телом. Вместо тела
появляется временная шкала: добавляйте сообщения кнопкой **Добавить сообщение** и задавайте каждому задержку, событие,
ID и данные. **Отправлять тело вместо этого** возвращает обычное тело.

Мок отвечает с `Content-Type: text/event-stream` и `Cache-Control: no-cache`, держит соединение открытым и записывает
каждое событие, когда приходит его время:

```text
event: status
id: 1
data: {"order": "ord_7Hk2Lw", "status": "shipped"}

```

Данные из нескольких строк отправляются несколькими строками `data:`. Поток, который проигрывается, пока клиент не
уйдёт, останавливается, когда клиент уходит или мок останавливается.

```sh
curl -N http://127.0.0.1:4010/orders/ord_7Hk2Lw/events
```

## Маршруты WebSocket [#websocket-routes]

Выберите **WebSocket** в меню вида маршрута, перед путём. Тогда маршрут принимает подключения WebSocket при `GET` на
свой путь и получает ответ с именем **Открыто** и статусом `101`.

<Shot id="mocks-route-websocket" alt="Редактор маршрута WebSocket: его вид и путь, ответ «Open» со статусом 101, сообщение, отправляемое после открытия сокета, и ответ на сообщение, у которого поле op равно watch" />

Что происходит, когда клиент подключается, решают ответы маршрута; они выбираются по своим
[правилам](/docs/mocks/routes#choosing-a-response), как у любого другого маршрута:

- Ответ `101` открывает подключение. Заголовки, которые вы добавите, уходят вместе с обновлением.
- Любой другой ответ отклоняет подключение этим ответом: например, `401` с телом, если нет токена. Ответ с правилом
  **Параметр запроса** `token` пуст отвечает клиентам, которые пришли без него.

`GET` без обновления к маршруту, ответ которого — `101`, получает `426 Upgrade Required`.

### Отправляется после открытия [#sent-once-open]

Сообщения в разделе **Отправляется после открытия** уходят клиенту, как только подключение открылось, каждое после
своей задержки: приветствие, начальное состояние, поток обновлений. **Закрыть само** заставляет мок закрыть
подключение через некоторое время, с кодом закрытия и причиной, например `4000` и `Shift over`.

### Ответы [#replies]

**Ответы** отвечают на то, что присылает клиент. Когда приходит сообщение, на него отвечает первый ответ, все условия
которого выполняются; сообщение, которое не взял ни один ответ, остаётся без ответа.

- **Добавить условие** проверяет поле сообщения, прочитанного как JSON: `op` равно `watch`, `user.id` равно `*`.
  Пустое имя поля проверяет весь текст — для сообщений, которые не являются JSON. Здесь действуют правила со
  [страницы маршрутов](/docs/mocks/routes#choosing-a-response): `*` — любое значение, пустое значение означает
  отсутствие.
- **Отправки** — временная шкала сообщений, которые уходят обратно. Они читают сообщение, на которое отвечают:
  `{{message.order}}` — его поле `order`, `{{message}}` — весь текст.
- **Затем закрыть** закрывает подключение после отправки, с кодом закрытия и причиной.

Например, ответ с условием `op` равно `watch`, который через 500 мс отправляет
`{"op": "shipped", "order": "{{message.order}}"}`, отвечает на `{"op": "watch", "order": "ord_7Hk2Lw"}` отправкой заказа
через полсекунды.

## Маршруты Socket.IO [#socketio-routes]

Выберите **Socket.IO** в меню вида. Маршрут Socket.IO — это пространство имён: его путь — пространство имён, к которому
присоединяются клиенты (`/support` или `/` для основного). Мок — это сервер Socket.IO 3 и 4 по адресу `/socket.io/`,
через WebSocket и long polling, с переходом от одного к другому, так что socket.io-client работает со своими обычными
параметрами.

Маршрут получает ответ с именем **Подключён** и статусом `101`:

- Ответ `101` позволяет клиенту присоединиться к пространству имён. **Отправляется после входа** — его временная
  шкала; каждое сообщение называет своё событие и передаёт аргументы как массив JSON (`[{"text": "Hello"}]`) или одно
  значение для одного аргумента.
- Любой другой ответ отклоняет: клиент получает ошибку подключения, сообщение которой — тело ответа (объект JSON как
  есть, например `{"message": "token rejected"}`, другой текст — как сообщение).

Правила выбирают ответ, как и у других маршрутов. Правила **Поле тела** читают данные авторизации клиента, так что
`token` равно `bad` может отклонить один токен. Пространство имён, которого нет ни у одного маршрута, получает ошибку
`Invalid namespace`.

**Ответы** отвечают на отправки клиента: **Когда клиент отправляет** называет событие (пусто — любое), условия читают
аргументы как массив (`0.topic` — это `topic` первого аргумента), а **Отправки** отправляют события обратно, читая
`{{message.0.topic}}`. **Ответить на подтверждение** отправляет первое сообщение обратно как аргументы подтверждения,
если отправка его запросила. **Затем отключить** и **Отключить само** выводят клиента из пространства имён.

## MQTT-брокер [#the-mqtt-broker]

Мок может запустить MQTT-брокер на собственном порту. Нажмите **Добавить брокер** в карточке **MQTT-брокер**; он
занимает порт `1883` или `1884`, если мок уже использует первый. **Удалить брокер** убирает его.

<Shot id="mocks-broker" alt="Карточка «MQTT-брокер»: порт 1889, два сообщения, публикуемые по временной шкале в топики склада, одно из них сохраняемое с QoS 1, и ответ на то, что клиенты публикуют в warehouse/+/restock" />

Это настоящий брокер для клиентов MQTT 3.1.1 и 5.0 по TCP: они подключаются, подписываются и публикуют, как с любым
брокером, с QoS 0, 1 и 2, сохраняемыми сообщениями и завещаниями. Запуск мока запускает и его; панель сверху
показывает его адрес, например `mqtt://127.0.0.1:1883`.

- **Публикуется** — временная шкала, которую брокер публикует с момента запуска мока: задержка, топик, данные,
  **QoS** и **Retain** каждого сообщения. Сохраняемое сообщение ждёт клиентов, которые подпишутся позже. **Проиграть**
  повторяет шкалу, `0` — пока мок работает.
- **Ответы** отвечают на то, что публикуют клиенты. **Когда клиент публикует в** принимает фильтр топиков
  (`warehouse/+/restock`), условия читают полезную нагрузку как JSON, а **Публикует** отправляет сообщения обратно, в
  топики, которые тоже могут читать сообщение: `warehouse/{{message.warehouse}}/orders`. `{{stream.topic}}` — топик, в
  который опубликовал клиент.

```sh
echolot mqtt subscribe mqtt://127.0.0.1:1883 'warehouse/#' --count 3
```

Изменение брокера, пока мок работает, перезапускает мок.

## Журнал [#the-log]

Каждое подключение — строка [журнала](/docs/mocks#the-log) с его статусом (`101` для открытого сокета, статус отказа)
и сообщениями в обе стороны, в виде строк JSON, в ответе, который она показывает. Каждый клиент MQTT — тоже строка, с
тем, на что он подписался, что опубликовал и что получил.

## Запросы и агенты [#requests-and-agents]

**Создать запросы** создаёт запрос WebSocket для маршрута WebSocket и запрос Socket.IO для маршрута Socket.IO, с
сообщением для каждого ответа с условиями, а для брокера — запрос MQTT, подписанный на все топики. См.
[WebSocket и SSE](/docs/requests/websocket-and-sse), [Socket.IO](/docs/requests/socket-io) и
[MQTT](/docs/requests/mqtt).

Агенты задают всё это: `save_mock_route` принимает `kind` маршрута, `events`, `repeats`, `ends`, `replies` и `close`
его ответов, а `save_mock` принимает `broker` или `removeBroker`. См. [Агенты](/docs/ai/agents).

## В рабочем пространстве [#in-the-workspace]

В файле мока `kind` маршрута — `websocket` или `socketio`; временная шкала ответа — `[[routes.responses.events]]`, его
ответы — `[[routes.responses.replies]]` с `[[routes.responses.replies.send]]`; брокер — `[broker]` с
`[[broker.publishes]]` и `[[broker.replies]]`. См. [файлы рабочего пространства](/docs/reference/workspace-files#mocks).
