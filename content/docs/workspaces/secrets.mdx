title: Secrets
description: Keep passwords, tokens and keys in the Keychain instead of workspace files, and give them to the command-line tool and CI.
---

A secret is a variable whose value stays in the Keychain on your Mac. The workspace file holds only its name, so you can
commit the workspace and share it without sharing your credentials. Use secrets for passwords, tokens, API keys and
anything else you wouldn't paste into a chat.

## Make a variable secret

1. Open the variable's table: the [Environments](/docs/workspaces/environments) page, **Folder Settings… › Variables**,
   or the request's **Variables** tab.
2. Add the variable, or find it, and check **Secret**.
3. Type the value in the field (it reads **Not set on this Mac**) and press <kbd>↩</kbd> or click **Save**.

The field never shows the value again. It reads **Stored in the Keychain**, with a key, once a value is there. To
change the value, type a new one and save it.

Use a secret like any variable: `{{token}}`.

<Shot id="workspaces-secret-variable" alt="Workspace variables on the Environments page: token marked Secret, its value field reading Stored in the Keychain" />

In the file, a secret is a name and a flag, with no value:

```toml
[[variables]]
name = "token"
secret = true
```

Each level keeps its own value. A secret `password` in the Staging environment and one in Production are two separate
values, so each environment can have its own password.

### Choose a value agents can't mistake

Agents read every secret masked, wherever it appears. A secret that is an ordinary word, such as `breadcrumbs`, hides
that word in every response and request description they read, and a value of fewer than four characters is too short
to mask at all. While you type a value like that, a warning under the field says so. A long random value avoids both.
The value is stored either way.

<Shot id="workspaces-secret-advice" alt="Workspace variables with a new secret, webhook_secret, its value being typed, and an orange warning under it: Short or an ordinary word: agents read it masked wherever it appears" />

## Where the values live

Values are kept in your login Keychain, in one item per workspace, labelled `Echolot secrets of workspace <ID>` (the ID
is in `workspace.toml`). Global variables have an item of their own, `Echolot global variables`. Within its item, each
value belongs to the level the variable is defined at. The command-line tool on the same Mac reads the same items.

The app and the command-line tool from echolot.dev share these items through a Keychain group of their own, so
neither asks for access, whichever of them stored the value. Items an earlier version kept in your login keychain move
into the group the first time they are read. Secrets from versions before that, kept one item per secret, move into
the workspace's item the same way.

Builds you make from source can't use the group and keep the login keychain. There, macOS trusts an item for the
program that made it and may ask the other one for access, once per workspace: choose **Always Allow**, and it covers
the secrets you add later too.

A secret with no value on this Mac doesn't fall back to another level. The request says
`the secret {{password}} has no value on this Mac` until you set one.

<Edition only="appstore">
  The App Store edition uses the same Keychain. Items the direct download or the command-line tool made may ask once
  for access; choose **Always Allow**.
</Edition>

## What never goes into files

Echolot keeps these out of workspace files:

- The values of secret variables.
- Secrets that [response captures](/docs/requests/captures) store: a capture marked secret writes to the Keychain only.
  In Alpenglow, **Auth › Sign in** captures `access_token` into the secret `{{token}}`.
- OAuth 2.0 tokens and MCP sign-ins.
- Values you move with **Move to Keychain** (below).

What you type as plain text stays plain text. When an auth or proxy password field holds a literal value instead of a
variable, Echolot warns under it: **Saved as plain text in the workspace file.** Click **Move to Keychain**: the value
becomes a workspace secret variable, and the field gets `{{name}}` in its place.

Secrets are also masked wherever Echolot shows or hands on a resolved request: previews, quick look, the Variables
panel, history search and everything agents receive. [Generate Code…](/docs/workspaces/exporting#copy-a-request-as-code)
and **Copy as cURL** are the exception: they write the request as it would be sent, secrets included.

## Imports move credentials into secrets

When you [import](/docs/get-started/importing) a Postman collection, an Insomnia export or another file, passwords,
tokens and API keys found in auth settings and credential headers become secret variables. Their values go to the
Keychain, and the request gets `{{name}}` instead: the request's name and the field, such as `{{me_password}}`. The
import report lists the names of
the secrets it saved, never the values.

Credentials written in addresses (`https://user:pass@…`), query strings and bodies are not moved yet. Check those
after an import.

## Exports leave values out

An [export](/docs/workspaces/exporting) writes secret variables by name only, with no value, in every format. The
person who opens the export sets the values on their side.

## Secrets on the command line and in CI

The command-line tool looks for a secret's value in this order:

1. A `--secrets` file given to `echolot run`: lines of `NAME=value`.
2. An environment variable `ECHOLOT_SECRET_<NAME>`: the name in capitals, with every character other than a letter or
   a digit turned into `_`. `{{token}}` reads `ECHOLOT_SECRET_TOKEN`; `{{api-key}}` reads `ECHOLOT_SECRET_API_KEY`.
3. On a Mac, the Keychain items the app keeps.

```sh
ECHOLOT_SECRET_TOKEN=… echolot run Alpenglow.echolot --folder orders
echolot run Alpenglow.echolot --env staging --secrets staging.secrets
```

The Keychain is skipped when `CI` is set, and when `ECHOLOT_KEYCHAIN=0`. In CI, set
`ECHOLOT_SECRET_…` variables from your CI's secret store. See [CI](/docs/cli/ci).

A secret found in the environment counts for every level: `ECHOLOT_SECRET_PASSWORD` answers `{{password}}` in any
environment.

Imports on the command line move credentials into secrets as the app does. Without a Keychain, the tool says which
`ECHOLOT_SECRET_…` variables to set.

## A teammate's first open

A teammate who clones the workspace gets every secret's name and none of the values. Their tables read
**Not set on this Mac**. They set their own values once, and from then on everyone works from the same files with their
own credentials. See [Git and teams](/docs/workspaces/git-and-teams).
