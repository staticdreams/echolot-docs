An MCP request is a saved call to one of the workspace's [MCP servers](/docs/mcp-servers): a tool call, a resource
read, a prompt, or any JSON-RPC method. Save the calls you make often, add checks, and run them in the
[runner](/docs/requests/runner) like any other request.

<Shot id="requests-mcp-call" alt="Agent tools › search_catalog: the server menu on Alpenglow MCP, Tool picked, the arguments as JSON with the tool's fields below, and the result with a green Result badge" />

## Try a call from the MCP Servers page

The quickest way to start is on the server itself:

1. Open the **MCP Servers** page and pick a server, such as **Alpenglow MCP**, which points to
   `https://demo.echolot.dev/mcp`.
2. Choose **Check** if it hasn't been checked yet. The page lists the server's **Tools**, **Resources** and
   **Prompts**.
3. Click a tool, resource or prompt. A sheet opens with its arguments.
4. Fill them in, as a **Form** built from the input schema or as **JSON**, and choose **Call**.
5. The result appears below, with **Result** or **Error** and the time it took.
6. Choose **Save as Request** to keep the call, with its arguments, as an MCP request.

## Create an MCP request

Choose **New MCP Call** from the **+** menu beside **Requests** in the sidebar. The editor's bar holds the call:

1. Pick the server from the menu at its start. **MCP Servers…** in the same menu opens the MCP Servers page.
2. Pick what to call: **Tool**, **Resource**, **Prompt** or **Method**.
3. Type the target: the **Tool name**, the **Resource URI**, the **Prompt name**, or a JSON-RPC method such as `ping`.
   Names from the server's latest check are offered as you type, under **From the Server**.
4. Choose **Call** (<kbd>⌘</kbd><kbd>R</kbd>). While it runs, **Cancel** (<kbd>⌘</kbd><kbd>.</kbd>) stops it.

| Operation | What it sends | What the arguments are |
| --- | --- | --- |
| **Tool** | `tools/call` with the tool's name | The tool's arguments |
| **Resource** | `resources/read` with the URI | Not used |
| **Prompt** | `prompts/get` with the prompt's name | The prompt's arguments |
| **Method** | Any JSON-RPC method | The method's params |

The editor has these tabs: **Docs**, **Arguments**, **Variables**, **Tests** and **Settings**. MCP requests have no
headers, auth or scripts of their own: the server's connection settings, its headers and its sign-in live on the
MCP Servers page. See [adding servers](/docs/mcp-servers/adding-servers).

## Arguments

The **Arguments** tab holds a JSON object, with `{{variables}}`:

```json
{
  "query": "ultralight tent",
  "limit": 3
}
```

When the server's latest check knows the tool, the tab shows its description above the editor and its fields
below, such as `Fields: query*, limit`; a star marks a required field. **Fill from Schema** replaces the arguments
with every field of the tool's input schema, to start from.

The Alpenglow workspace has two calls in **Agent tools**: **search_catalog**, with the arguments above, and
**order_status**, which looks up `{"order_id": "ord_7Hk2Lw"}`.

## Results

The response pane shows the result as JSON in the **Body** tab, like any [response](/docs/requests/responses). The
badge in the response summary reads **Result** in green or **Error** in red, with the protocol version the server
speaks. Point at it to see who answered, or what went wrong.

A call can fail in two ways, and Echolot keeps them apart:

- The server answers with an error: a tool result marked as an error, or a JSON-RPC error. The badge reads **Error**,
  and the body holds what the server said.
- The call never gets an answer: the server can't be reached, doesn't start or breaks the protocol. The response
  pane says why. Check the server on the MCP Servers page: its message log shows every message of the last check.

Every call is kept in [History](/docs/workspaces/history).

## Checks for MCP

In the **Tests** tab:

- **MCP error** tells how a call failed. Its value is `false` when the call succeeded, `tool` when the tool itself
  failed (a result marked as an error, which a model reads and can act on), or `protocol` when the server answered
  with a JSON-RPC error (it broke or refused the call). **equals** `true` takes either failure. So **MCP error**
  equals `false` passes on success, and equals `tool` passes on a tool that reports a bad input as it should.
  **exists** passes on any failure and **does not exist** on none. A failed check shows the server's message.
- **Tool output schema** checks the result's `structuredContent` against the `outputSchema` the tool declares. It
  fails when the tool declares none, or the result has no `structuredContent`.
- **JSON value** checks any value of the result, such as `$.structuredContent.results.length` is greater than `0`, or
  `$.content[0].type` equals `text`.

See [scripts and tests](/docs/requests/scripts-and-tests) for every check and comparison.

## From the command line

`echolot run` runs saved MCP requests with their checks, `echolot mcp call` calls a tool, reads a resource or gets a
prompt, and `echolot mcp check` inspects a server. See [echolot mcp](/docs/cli/mcp).
