“规范”页面用于设计并保存 API 的契约：OpenAPI 文档（OpenAPI 3.0 和 3.1，以及 Swagger 2.0）和 gRPC 服务的 `.proto` 文件。Echolot 会在你编辑时检查规范，把它转换为与之保持同步的请求，并在 API 出现之前将它作为[模拟服务器](/docs/mocks)提供服务。

在边栏的模块切换器中选择<strong>规范</strong>，或按 <kbd>⌘</kbd><kbd>3</kbd>，即可打开。

<Shot id="specs-page" alt="“规范”页面，alpenglow.yaml 在可视化编辑器中打开：边栏列出该规范及其端点和 Schema 的大纲；页面显示“概览”“服务器”和“端点”卡片" />

## 工作区中的规范 [#specs-in-the-workspace]

规范是工作区 `specs` 文件夹中的文件，因此会和其他一切一起进入 Git。Alpenglow 示例有三个：`alpenglow.yaml`（商店的 OpenAPI 文档）、`shop.graphql` 和 `inventory.proto`。“规范”页面在<strong>规范</strong>下列出 OpenAPI 文档，在 <strong>Proto 文件</strong>下列出 `.proto` 文件。文件夹中的 GraphQL Schema 供 [GraphQL 请求](/docs/requests/graphql)使用，不在这里列出。

边栏<strong>规范</strong>标题中的 <strong>+</strong> 用于添加：

| 项目 | 作用 |
| --- | --- |
| <strong>新建规范</strong> | 创建一个标题为 `New API` 的 OpenAPI 3.1 文档，并在可视化编辑器中打开。 |
| <strong>从响应新建规范…</strong> | 根据你发送过的请求和得到的响应写出规范。参见[从响应生成规范](/docs/specs/specs-from-traffic)。 |
| <strong>添加规范文件…</strong> | 把 Mac 上的 OpenAPI 或 Swagger 文档（YAML 或 JSON）拷贝到 `specs` 文件夹。 |
| <strong>新建 Proto 文件</strong> | 从一个简单的示例服务创建 `.proto` 文件。参见 [.proto 文件](/docs/specs/proto-files)。 |
| <strong>添加 Proto 文件…</strong> | 把 `.proto` 文件拷贝到 `specs` 文件夹。 |

用<strong>文件 › 导入…</strong>[导入](/docs/get-started/importing) OpenAPI 文档则不同：它根据文档创建请求，而不是创建可供编辑的规范。

右键点按规范可选择<strong>生成请求</strong>、<strong>在访达中显示</strong>、<strong>导出</strong>（<strong>JSON 格式…</strong>或<strong>YAML 格式…</strong>）和<strong>删除…</strong>。删除前会先询问，并把文件移到废纸篓；它所引用的文件和基于它的模拟服务器都会保留。

## 大纲 [#the-outline]

点按规范即可打开。在列表下方，边栏显示它的大纲：

- <strong>概览</strong>，即标题、版本和描述。
- <strong>端点</strong>，每个操作及其方法和路径。已弃用的带删除线。将指针停留在其上可查看摘要。
- <strong>SCHEMA</strong>，可复用的 Schema。
- <strong>文件</strong>，当规范引用其他文件时（参见[拆分到多个文件的规范](#specs-split-across-files)）。

点按某个条目即可打开：在可视化编辑器中，对应的卡片会打开并滚动到视野内；在代码中，编辑器会跳到它所在的行。

## 可视化和代码 [#visual-and-code]

页面标题栏中的<strong>编辑器</strong>开关决定如何查看打开的规范：

- <strong>可视化</strong>：概览、服务器、端点和 Schema 的卡片，用字段和菜单编辑。
- <strong>代码</strong>：YAML 或 JSON 格式的文档，带行号。

两者编辑的是同一份文本，Echolot 会在每次更改后不久存储它。[编辑规范](/docs/specs/editing)对两者都有介绍。

## 问题 [#problems]

Echolot 会在你编辑时对规范做 lint 检查。编辑器上方的栏显示<strong>没有问题</strong>，或错误和警告的数量。边栏中打开的规范旁边也会显示红色的错误数。

<Shot id="specs-problems" alt="规范上方的“问题”弹出窗口：错误和警告，每项都带有消息和行号" />

点按它可查看列表：先是错误，然后是警告和提示，每项都带有行号。选择其中一项可跳到那一行。列表为空时，会说明文档符合 OpenAPI 规范，且每个引用都能解析。

lint 检查的内容包括：

- Echolot 能读取的 `openapi` 版本、带有标题和版本的 `info`，以及以 `/` 开头的路径。
- 出现在路径中且标记为 `required: true` 的路径参数，以及没有重复定义的参数。
- 每个响应都有描述，且每个操作 ID 只使用一次。
- 在顶部声明的标签、已定义的安全方案、带 `items` 的数组，以及带值的枚举。
- 指向实际内容的引用，在本文件中，或在 `specs` 里的另一个文件中。
- 没有 `servers`：此时根据规范创建的请求以 `{{baseUrl}}` 开头，由你自己设置。

命令行工具在 CI 中运行相同的 lint：参见 [echolot spec](/docs/cli/spec)。

## 拆分到多个文件的规范 [#specs-split-across-files]

规范可以用 `$ref` 引入其他文件的部分内容，例如 `$ref: schemas/pet.yaml#/Pet`。这些文件必须位于工作区的 `specs` 文件夹内。边栏在<strong>文件</strong>下列出它们：点按其中一个，即可在<strong>代码</strong>中打开。在代码编辑器中，将指针停留在 `$ref` 上可查看它指向什么，按住 <kbd>⌘</kbd> 点按则会跳转过去，无论在本文件还是另一个文件中。

凡是用到规范的地方，Echolot 都会把各部分合在一起读取：lint、生成请求、模拟服务器。导出规范时，它引用的文件会写入你存储的那一个文件。

## 导出 [#exporting]

编辑器上方栏中的<strong>导出</strong>（<strong>导出为 YAML…</strong>或<strong>导出为 JSON…</strong>）会把规范存储为工作区之外的一个文件，它引用的文件会写入其中。未存储的编辑会先存储，因此导出的就是编辑器显示的内容。

## 遵循规范的请求 [#requests-that-follow-the-spec]

编辑器上方栏中的<strong>生成请求</strong>会创建一个以规范命名的文件夹，其中为每个端点创建一个请求，并打开第一个。该文件夹会遵循规范：规范更改时，你可以把更改应用到它的请求上，而不会丢失你在请求中所做的编辑。

文件夹一旦遵循规范，该按钮就变成<strong>请求</strong>，这是一个菜单，其中为每个遵循规范的文件夹提供<strong>检查“文件夹”的更改…</strong>，另有<strong>再生成一个文件夹</strong>。检查会打开 <strong>OpenAPI 同步</strong>，列出<strong>规范中新增</strong>、<strong>规范中已更改</strong>和<strong>已从规范中移除</strong>的内容。勾选你想要的更改并点按<strong>应用 1 项更改</strong>（或<strong>应用 3 项更改</strong>，依此类推）。你的编辑始终会保留；当你和规范更改了同一处时，保留你的。某个操作被移除后，它的请求会移到废纸篓，除非你编辑过它：那样它会保留，但不再遵循规范。<strong>取消链接</strong>会让文件夹不再遵循规范，并保持其请求不变。

文件夹也可以遵循工作区之外的规范，即一个文件或一个 URL：在“请求”边栏中右键点按该文件夹，选择<strong>链接到 OpenAPI 规范…</strong>。命令行工具用 `echolot spec check` 和 `echolot spec apply` 检查并应用更改。

## 依据规范检查响应 [#checking-responses-against-a-spec]

请求的<strong>测试</strong>标签页中的 <strong>OpenAPI 规范</strong>检查会依据规范为其操作和状态记录的 Schema 来验证响应。参见[脚本和测试](/docs/requests/scripts-and-tests)。
请求需要知道这两者：

- 操作，即请求文件中的 `spec-operation`，比如 `GET /products/{sku}`。根据规范生成的请求带有它。
- 规范。它是请求所在的文件夹（或其上方的某个文件夹）所遵循的规范。请求也可以在它的文件中用 `spec` 指定自己的规范，比如 `spec = "specs/alpenglow.yaml"`。
  此时它依据该规范进行检查，而它的文件夹并不遵循该规范，因此文件夹中的任何内容都不会同步：这适用于发往[模拟服务器](/docs/mocks)的请求，或文件夹中少数手工创建的请求。

```toml
spec = "specs/alpenglow.yaml"
spec-operation = "GET /products/{sku}"
```

## 将规范导入工作区 [#importing-a-spec-into-a-workspace]

用<strong>文件 › 导入…</strong>导入 OpenAPI 文档，会创建以 `{{baseUrl}}` 开头的请求，并根据规范的服务器设置 `baseUrl`。如果工作区或它的某个环境已经有基础地址变量
（`baseUrl`、`baseURL`、`base_url`、`apiUrl` 之类），请求会改用那个变量，导入也不会设置任何变量，因此由你的环境决定请求发往哪里。导入报告会说明这一点，
并附上规范自己的服务器地址。参见[导入](/docs/get-started/importing)。
